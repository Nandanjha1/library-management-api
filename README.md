# Library Management System

A full-stack Library Management System built with **Python, FastAPI, PostgreSQL, React, and Vite**. It provides REST APIs and a web interface for managing books, physical copies, members, loans, fines, partner catalogue access, and library reports across multiple branches.

## Overview

The Library Management System replaces spreadsheet-based library operations with a relational database and a RESTful API. It supports multiple library branches and models books separately from their authors and physical copies.

The backend is built with FastAPI and PostgreSQL. The React frontend provides interfaces for catalogue browsing, inventory management, member access, loans, fines, and reports. Different authentication mechanisms are used for members, librarians, and partner catalogue services.

## Features

### Book catalogue and inventory
- Search and browse the book catalogue.
- Retrieve book details, authors, and branch-level availability.
- Add and update book information.
- Add physical copies using unique barcodes.
- Track copy status and availability.

### Member management
- Register members and authenticate with JWT access tokens.
- Retrieve the authenticated member's profile.
- Access personal loan and fine records.
- Enforce access controls for member-specific resources.

### Loans and returns
- Check out available physical book copies.
- Return borrowed copies.
- Track active and overdue loans.
- Enforce the active-loan limit and prevent simultaneous active loans for the same physical copy.

### Fines and payments
- Calculate late fines according to the configured policy.
- Retrieve fine records and outstanding balances.
- Record librarian-authorized desk-payment entries.

### Librarian operations and reports
- Authenticate librarians with database-backed sessions and HTTP-only cookies.
- Manage books and physical inventory.
- Retrieve overdue-loan reports and most-borrowed book reports.
- Retrieve dashboard statistics.

### Partner catalogue
- Protect partner catalogue access with an API key and secret.

### Testing and documentation
- Pytest-based automated tests.
- Interactive API documentation generated by FastAPI.
- Postman resources for API testing.

## Architecture

The project uses a layered architecture to separate HTTP handling, validation, authentication, database operations, and user-interface concerns.

```text
Member / Librarian / Partner Service
                 |
                 v
          React Frontend
                 |
               Axios
                 |
                 v
            FastAPI API
                 |
       +---------+----------+
       |         |          |
       v         v          v
    Schemas   Security   API logic
                 |
                 v
            Repositories
                 |
                 v
             PostgreSQL
```

### Main layers

1. **API layer (`app/api/`)** — Defines routes, handles requests, and returns HTTP responses.
2. **Schema layer (`app/schemas/`)** — Validates request data and defines response structures.
3. **Core and security layer (`app/core/`)** — Provides configuration, token validation, session verification, and authentication dependencies.
4. **Repository layer (`app/repositories/`)** — Executes parameterized SQL queries and database operations.
5. **Database layer (`app/db/`)** — Manages database connectivity.
6. **Frontend (`frontend/src/`)** — Contains React pages, reusable components, layouts, and API/authentication helpers.
7. **SQL resources (`sql/`)** — Contains database schema and seed data scripts.

## Business Rules

- A member can have at most **three active loans** at a time.
- A physical book copy cannot have more than one active loan simultaneously.
- Returning a copy updates the loan and copy status.
- The late-fine policy is **₹10 per overdue day**, using the date calculation implemented by the application.
- Members may access only their own protected member records.
- Protected librarian operations require a valid librarian session.
- Partner catalogue requests require valid partner credentials.

## Installation and Setup

### 1. Clone the repository

Replace the placeholder with your actual repository URL.

```bash
git clone https://github.com/Nandanjha1/library-management-api.git
cd library-management-api
```

### 2. Create and activate a Python virtual environment

**Windows PowerShell:**

```powershell
python -m venv venv
.\venv\Scripts\Activate.ps1
```

If PowerShell blocks activation because of its execution policy, use your organization's approved approach or activate the environment from Command Prompt instead:

```bat
venv\Scripts\activate.bat
```

### 3. Install backend dependencies

From the project root:

```bash
python -m pip install -r requirements.txt
```

### 4. Configure PostgreSQL

Create the database and database user according to your local PostgreSQL setup. The application configuration and SQL scripts must target the same database.

Apply the SQL files in this order:

1. `sql/schema.sql`
2. `sql/seed.sql`

You can execute the scripts using pgAdmin or `psql`. For example, after creating the database and configuring the appropriate connection:

```bash
psql -U <DATABASE_USER> -d <DATABASE_NAME> -f sql/schema.sql
psql -U <DATABASE_USER> -d <DATABASE_NAME> -f sql/seed.sql
```

Replace the placeholders with your local values. Do not run schema creation against a database containing data you need to preserve unless you have reviewed the script first.

### 5. Configure environment variables

The repository currently contains a local `.env` file. Keep it private and excluded from Git. Create a committed `.env.example` containing **placeholder values only**, based on the exact variables read by `app/core/config.py`.

The following is an illustrative example of common configuration values, **not a guarantee that these are the exact variable names your current code reads**:

```dotenv
APP_NAME=Library Management API
APP_ENV=development
DATABASE_URL=postgresql://library_user:URL_ENCODED_PASSWORD@localhost:5432/library_db
JWT_SECRET_KEY=REPLACE_WITH_A_STRONG_RANDOM_SECRET
JWT_ALGORITHM=HS256
ACCESS_TOKEN_EXPIRE_MINUTES=30
```

Before using this example, check `app/core/config.py` and use the exact variable names and format required by your implementation. If your database connection uses separate host, port, database, username, and password variables rather than `DATABASE_URL`, document those instead.

Use strong, unique secrets in local configuration. URL-encode reserved characters in a database password if it is embedded in a connection URL. Never commit real passwords, JWT signing keys, partner secrets, or session values.

### 6. Install frontend dependencies

Open a second terminal:

```powershell
cd frontend
npm install
```

If the repository has a committed lockfile, `npm ci` can be used for a reproducible installation.

## Authentication

The application uses separate authentication mechanisms for different clients.

### Member authentication
- Members register and log in through the member authentication endpoints.
- Successful login provides a JWT access token.
- Protected member endpoints validate the token before returning member-specific data.
- A member must not be able to retrieve another member's private records by changing an ID or request parameter.

### Librarian authentication
- Librarians log in through a session-based flow.
- The session is represented by an HTTP-only cookie.
- Protected librarian operations require a valid session.
- Logging out should revoke or invalidate the active session.

### Partner catalogue authentication
- Partner catalogue requests require the configured API key and secret.
- Keep partner credentials confidential and use only the credentials configured for your local test environment.

## Database Design

The relational schema separates books from authors and physical copies. This supports many-to-many book/author relationships and multiple physical copies of a title across library branches.

The database includes tables for the following entities, as implemented in the SQL schema:

- Branches
- Books
- Authors and book-author relationships
- Physical book copies
- Members
- Staff
- Loans
- Fines
- Partner clients
- Librarian sessions
- Fine-payment records

The schema uses relational constraints such as primary keys, foreign keys, uniqueness rules, and check constraints. Indexes and the active-loan uniqueness rule help enforce data integrity and support common queries. Refer to `sql/schema.sql` for the authoritative definitions.

## Security Decisions

- **Parameterized SQL:** User-supplied values should be passed as query parameters rather than interpolated into SQL statements.
- **Password hashing:** Passwords are stored as hashes, not plaintext; the project uses `pwdlib` with Argon2 according to the current implementation.
- **Member authorization:** JWT validation protects member-specific endpoints.
- **Librarian sessions:** Session-based authentication allows librarian sessions to be checked and revoked.
- **Partner authentication:** Partner credentials are verified by the backend.
- **Environment configuration:** Keep database credentials and signing secrets outside committed source code.
- **Backend authorization:** Frontend route guards improve user experience but do not replace API-side authorization.
- **Transaction safety:** Multi-step operations should commit or roll back together when partial completion would corrupt library state.

### Desk-payment limitation

The desk-payment endpoint records a librarian-authorized payment entry. It does not independently verify a card or UPI transaction. Real online payments require a trusted payment gateway and verified transaction confirmation before a payment is marked as successful.

## Postman Testing

Postman resources are stored in the `postman/` directory. Import the collection available in that directory, if present, and configure its base URL and test credentials for your local environment.

Recommended test areas:

- Health and database connectivity.
- Book catalogue search and book details.
- Member registration, login, and profile access.
- Librarian login, logout, and protected book management.
- Checkout and return flows.
- Loan-limit enforcement.
- Fine calculation and payment-record handling.
- Librarian reports.
- Partner catalogue authentication.
- Expected failures, including missing authentication, invalid input, nonexistent IDs, and duplicate barcodes.

Use test accounts and local test data. Never include real credentials or live secrets in a committed Postman collection.
